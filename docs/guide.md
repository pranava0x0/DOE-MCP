# Local workflows and evidence

DOE-MCP reads public publisher APIs through focused domain servers. Each
answer separates the data from its sources, record evidence, access
recipes, warnings and coverage. It does not operate facilities or run
simulations. The source registry names unbuilt capabilities and why they
cannot yet be queried.

## Start with a recorded workflow

Install from the checkout with `pipx install .`. The package is not yet
published on PyPI. Recorded workflows and skills ship in the wheel.

```bash
doe-mcp demo evidence --output ./evidence-run
doe-mcp demo client
doe-mcp skills
doe-mcp skills find-doe-data --show
```

The first command writes JSON evidence and a CSV evidence index. The
second launches a real stdio server, initializes an SDK client, calls a
local registry tool, validates its structured response, checks a typed
error, and closes the process. Neither command needs an API key or a
publisher connection.

Available walkthroughs: `evidence`, `partial`, `blocked`, `grid`, `eia`,
`site`, `earth`, and `materials`. The partial case explicitly simulates one
unavailable source in an isolated replay. The blocked case reads registry
inventory; it does not query the proposed publisher.

[Browse the recorded walkthroughs](demos.html). Every export names its
mode, registry revision, fixture hashes and available capture times.
Older fixtures have no recorded capture time; those remain unknown.
Envelope retrieval timestamps in a replay are a labelled fixed reference
clock, never evidence of a current publisher fetch. Record dates remain
separate. A captured result cannot establish current endpoint health.

## Use live publishers locally

```bash
doe-mcp demo evidence --live --output ./live-evidence
doe-mcp demo grid --live --output ./live-grid
```

Live EIA demand also requires the user's configured EIA key:

```bash
doe-mcp configure credentials
doe-mcp demo eia --live --output ./live-demand
```

The grid walkthrough reports BPA load in MW and the publisher's Pacific
Time labels. EIA reports hourly energy in MWh. Neither series establishes
local connection capacity. Keep forecasts distinct from observations.

The site walkthrough plots a bounded sample of Rhode Island facility
coordinates. The plot extent is the returned sample's extent, not a
parcel search. Ownership, queue position, tariffs and available capacity
remain unknown. Its NEPA-MCP link is a manual handoff to another project.

Earth search results and Oak Ridge modelled weather are separate examples,
not a claimed study-site match. The materials walkthrough likewise keeps
the computed GaN structure separate from the H/C/O basis-set example.

The outage-history, facility-status and microbiome tools have checked
skill tasks but no walkthrough page yet; [the examples](../examples/README.md)
show one call for each. Outage history returns the EAGLE-I release that
covers a year and its DOI, not outage figures. The microbiome tools return
study and sample metadata; sequence data stays behind each study's DOIs.

## Connect a client and provide a skill

```bash
doe-mcp configure claude-code research --dry-run
doe-mcp configure claude-code research
```

The other supported configuration targets are `claude-desktop`, `vscode`
and `cursor`. Start with the domain you need. Registering all servers also
loads a larger combined tool set into clients without deferred discovery.
Credentials stay in the user's credentials file, outside client configs.

`doe-mcp skills NAME` prints the installed file path. Ask a client that can
read local files to read that file before starting the task, or provide
its content from `--show`. Skills are packaged documents; they are not
loaded automatically as MCP resources or installed as client plugins.

## Interpret the result

The fetcher supports GET only. Source gates check registry eligibility
before a publisher is queried. Adapters interpret each publisher's response;
domain tools assemble the evidence envelope; MCP serves its typed shape.

Coverage has separate dimensions: registry, execution, pagination,
publisher scope and result. A hit does not imply a complete search. An
empty result does not establish that DOE has no data. A proposed source
in the registry does not contribute live evidence. Follow publisher-supplied
locators; never construct a plausible record URL from an identifier.

The JSON export keeps each call, its arguments and its envelope. CSV is
an evidence index, not a substitute for JSON's coverage and warnings. Each
CSV row names its workflow step, source and record. Potential spreadsheet
formula cells are escaped.

See the generated [tool reference](reference.md) for exact names and
arguments. The static site is generated by `tools/build_site.py`; change
its renderer or registry inputs, not generated pages.

## Evaluate agent behavior

Prepare the existing skill tasks without calling a model:

```bash
doe-mcp evaluate --prepare --output ./evaluation-tasks.json
```

The twelve cases cover useful answers and six traps. Evaluation annotations
live beside the checked and reader tasks in each skill's `bench.yaml`.
Contract tests run offline. They do not prove model-selection accuracy.

Optional model runs use an explicitly supplied executable driver:

```bash
doe-mcp evaluate --driver ./model-driver --model YOUR_MODEL \
  --max-calls 12 --max-tokens 20000 --repeats 3 \
  --exposure focused --output ./evaluation-run.json
```

The driver reads one JSON request on stdin and writes one JSON response on
stdout. The request carries messages, visible tool schemas, a remaining
token budget and an output-token limit. The driver calls the chosen model
and returns either `tool_calls` (name and arguments) or `answer` (text and
citations), plus actual `usage.input_tokens` and `usage.output_tokens`. Return
`model_version` and `settings` to identify the model and sampling
configuration; absent values are explicitly reported as unknown.
Each citation names a one-based tool step and an evidence ID from that
step. Keep provider credentials in the driver's own environment; never
return them or log them. Driver stderr is not retained.

The harness executes requested tools against recorded responses. It
refuses unavailable tools and stops after a driver failure or unknown
usage. The call cap is enforced before each request; token accounting
relies on the driver, which must enforce the remaining total budget at the
provider. A provider call cannot be unspent when a driver over-reports its
budget. No paid model driver is bundled or run by default.

Run focused/all tool exposure with skills enabled/`--no-skills`, three
repetitions each. Cases not run because of a budget remain in the report's
denominator. Reports preserve failures and require human review against
each task's rubric. Automatic citation checks are not semantic grading;
no accuracy score is advertised before that review. Source text is
untrusted, including the injected-instruction trap.

For a release, require no fabricated locators, leaked keys, forecast-as-
demand claims or invented source coverage. Inspect all trap answers and
report numerator and denominator for useful-task success. The architecture's
90% target is a proposed small-sample release gate, not a measured result.

## Development checks

```bash
python -m pytest
ruff check .
mypy
doe-mcp sources validate
python tools/build_schema.py
python tools/build_site.py --fixtures
python3 tools/slopcheck.py --include-agent-docs .
```

Measure local replay overhead separately from model or publisher latency:

```bash
python tools/benchmark_workflows.py --output ./replay-baseline.json
```

This records three cold/warm pairs per workflow, startup time and output
bytes. It makes no claim about live performance. CI also builds a wheel
from a source distribution and runs `tools/check_installed.py` in a clean
environment outside the checkout.

The initial type-check scope is the envelope and OSTI page adapter. It is
not a claim that the whole project is typed. Source liveness remains a
separate scheduled check. Fixture recording rewrites a whole source file;
use the existing recorder guards and run the full suite immediately after
recording. A targeted recording uses `--source SOURCE_ID`.
